# App/Layout

Where windows go. A **layout** is a named `LayoutTemplate` of pieces (Greenroom's Meeting window, Chat, individual meeting "views", and other apps) stored as fractions (`UnitRect`, 0...1, top-left origin) of a display's usable area, with one arrangement per display (ADR 0002): a main-display arrangement (`LayoutTemplate.oneDisplay`, the old key kept) and an optional second-display arrangement (`twoDisplays.second`, used only while that display is connected). `LayoutLibrary` holds all templates plus the active one (the Start layout; never nil after migration: "None" is gone and Leave my windows alone, which moves no window, is the fallback). At Start, Snap Back, Apply now or a display plugged in or pulled out, `LayoutEngine` resolves the active template against the displays connected right now (`LayoutResolver`, pure) and moves windows: Greenroom's own windows by `setFrame`, other apps through the Accessibility API (`AppWindowManager`) or AppleScript (Chrome, via `ChromeWindowManager`). The folder also holds display-change handling (`DisplayMonitor`, `DisplayPlan`, `DisplayResolver`) and the Start-step time limit (`StartTimeout`). The pure files (`LayoutTemplate`, `LayoutGeometry`, `DisplayPlan`, `StartTimeout`, `WorkspaceLayout`) are Foundation-only so tests and off-screen renders compile them without the app or the Zoom SDK.

## How it fits

**State owner.** `CoordinatorController` owns `@Published var layoutLibrary: LayoutLibrary` (loaded with `LayoutLibrary.loadOrMigrate(from: defaults, defaultSiteURL:)`, saved to UserDefaults key `layoutLibrary` from its `didSet`) and `@Published private(set) var sessionTemplate: LayoutTemplate?` (the template running now). It owns `private lazy var layoutEngine = LayoutEngine(chat: zoomChatBridge, log:)`. If the library is edited while a session runs, `sessionTemplate` is refreshed from the library (the live edit path), but no window moves until Snap Back (R45, `noteLiveLayoutEdit` logs it once). Settings export/import carries `layoutLibrary` and the legacy shape (`LegacyLayoutSettings`).

**Start-time flow.** `start()` picks `sessionTemplate`, sets `speakerTileQuickHidden = layoutEngine.startsHidden(template)`, `meetingWindowWanted = !layoutEngine.hasViewsButNoMeeting(template)`, opens App pieces (`openApps`, those with `opensAtStart`; an app with its eye off is placed, then `MainPaneManager.minimiseFrontWindow` minimises it, and `activateLargestApp` skips it), joins the meeting (see codemap/zoom.md), then `layoutEngine.openChat(...)`, `presentMeetingSurfaces` -> `placeMeetingAndChat`, `activateLargestApp`. `sessionArranges` (a template is active) also tells `ZoomMeetingSDKClient.arrangesWindows` and `setDualScreenMode(sessionArranges && galleryWindowExists)`.

**Resolution (pure).** `LayoutEngine.resolve(template)` -> `LayoutResolver.resolve(template, screens: connectedScreens(), primaryHeight:)`. The main arrangement always goes on the main display. The second arrangement goes on the second display only while one is connected (`TwoDisplay.secondUUID`, else the first non-main display); with none, its pieces are ignored with no note (R26; a Meeting only on second then places no Meeting window). `LayoutResolver.secondIsConnected` feeds `substitutingMeetingForActiveSpeaker(secondConnected:)`, so a second display that is not there does not stop main's Active speaker standing in. Each piece gets `LayoutFrames` in both coordinate spaces: `ns` (bottom-left, `NSWindow.setFrame`) and `ax` (top-left of the primary display, Accessibility/AppleScript). `Result.notes` carries fallbacks worth logging (log only when `logNotes: true`; per-second loops pass false). Nothing is cached: displays and Dock/menu-bar usable area change.

**Applying.**
- Greenroom's own windows: Meeting window via `ParticipantGridWindowController.place(frame:)/show/hide`; Chat via `ChatWindowController.show/setFrame/reveal`; view pieces via `MeetingViewWindows.place(view, frame:hidden:)` and `MeetingViewWindows.setHiddenTogether`; built-in browser via `BrowserWindowController.show`. `LayoutShareChoice.record(result)` runs before windows open ("Show to everyone" per piece; it also hands `Visibility.hiddenAppIDs` to `ShareVisibleWindows.setHiddenApps`, so every layout pass, including a live 📡 flip, updates the capture; see Stage `ShareVisibleWindows`). Only placed windows follow their piece (`LayoutShareRule.startsShown`, default shown); with Leave my windows alone as the active layout (it moves no window), and at session end, `LayoutShareChoice.reset()` puts Meeting window, Chat and views back to "Only you". A live session keeps its layout, so a layout is never turned off mid-session.
- Other apps: `MainPaneManager.openWindow` (browsers: Chromium AppleScript route via `ChromeWindowManager` first, then NSWorkspace + AX; `placeFrontWindow` returns the ACTUAL frame, which the app may have clamped) and `repositionFrontWindow` (Snap Back).
- Hide/show the Meeting (hotkey Ctrl-Opt-Cmd-H): `LayoutResolver.frames(of:meetingHidden:)` lets the neighbour grow into the gap (`absorbingNeighbour`); `moveNeighbour` applies it, `LayoutGeometry.differs` detects an app that refused a size.
- Close: `closeApps` at End Session, only windows Greenroom itself opened (browser; Chromium by remembered id); never closes other apps.

**Placed once (R45).** Every path that moves a window during a meeting asks `LayoutPlacementRules`. Only Start (`presentMeetingSurfaces(trigger: .start)`), a layout switch (`applyLayoutNow`: `.switchedLayout`), Snap Back (the ⌃⌥⌘S shortcut via `ShortcutRuntime` and the menu bar's Snap Windows Back, both `snapWindowsBack()` -> `reapplyLayout(trigger: .snapBack)`) and a display plugged in or pulled out re-place windows that are up, and order them front (`orderFrontRegardless`, never activating). An edit to the running layout waits for Snap Back. The Meeting coming back (`openMeetingWindow`, the speaker-tile toggle: `placeCustomSurfaces(trigger: .meetingShown)`) moves nothing that is up and only opens a view that never opened. The meeting window's one-second loop keeps the window's current form unless an explicit pass set `ParticipantGridWindowController.pendingPlacement`. The neighbour that grows into the Meeting's gap (`moveNeighbour`) is left alone when the owner moved it: `LayoutEngine.placedFrames` keeps the frame each app or Chat was last placed at (read back after placing; apps via AX), compared by `LayoutPlacementRules.state`. Apps a layout opens are placed once when their window first appears, however late, and never activated (`MainPaneManager.openWindow(activates: false)`: NSWorkspace `activates`, Chrome's AppleScript `activate`, the Greenroom Browser's `show(focus:)`); the one focus hand-off is `activateLargestApp(_:after: .start)` at the end of Start. "Open This Layout's Apps" is the owner's own open and activates.

**Display changes.** `CoordinatorController` registers `DisplayMonitor.shared.onChange` (~4370) -> `displaysChanged(change)`: logs, `stage?.displaysDidChange(connected: DisplayMonitor.connectedForCapture(), main: LocalDeviceResolver.mainDisplayUUID, ...)` (Stage then uses `DisplayPlan.decide`), `DisplayMonitor.rescueStrandedWindows`, `syncReadinessHUD()`, then either flags `displayChangedDuringStart` (while Start runs) or, when live, `snapWindowsBack(userInitiated: false, trigger: .displaysConnectedOrDisconnected)` only if the set of displays changed (a resolution, arrangement or Dock change moves nothing but stranded windows, R45). `ZoomMeetingSDKClient.installStageVideoWithRetry` waits on `DisplayMonitor.awaitQuiet` before touching the SDK video slot.

**Editor chrome (Direction A).** Per canvas header (`LayoutCanvas.header`, filled by `LayoutPageContent.canvas(...)`): the name (the second display shows a "SECOND ▾" menu: display picker + Remove second display, which asks first when it has pieces and is one undo step), then on the shared canvas the "Everyone sees this ▾" tag (`sharedTag`: opens the one share pop-out `SharePopout` as a popover through `LayoutSharePopout`, `.atStart` context: shared display when two displays, What's shared, the app, Follow the slide show; saved per layout; it is what marks the shared display, so there is no separate SHARED tag), then the canvas's own + (`addButton`; `addPanelSlot` says whose panel is open): one line per canvas. Preview: My screen / Everyone (a `GreenroomSegmented`) + Show on screen (`previewControls`, no shortcut) sit on the layout's title row. The main canvas always shows and fills the panel; with no second arrangement a thin dashed strip (`AddSecondStrip` in LayoutCanvas.swift, passed as `LayoutCanvas.trailingStrip`, tooltip "Add a second display") sits at its right edge and adds an empty one; with a second, `LayoutPageContent.canvases` sizes both side by side from `LayoutEditorRules.canvasWidths` (panel width read through `LayoutPanelWidth`). The title row holds the name, the ⋯ menu (`layoutMenu`), Apply now (only while a meeting runs another layout) (there is no One/Two displays toggle). The inspector is below the canvases; with nothing selected it shows the layout's description (`caption`) and the key hints are its tooltip. Restore original is in the rules but not shown until `LayoutLibrary.restoreOriginal` exists (P9).

**Editor basics (P6, R9).** Undo: `LayoutEditRecorder` (App/UI, tested by `LayoutEditRecorderTests`) also records the camera state and the camera look as steps (`record(_:undo:redo:)`; the page wraps those bindings) and calls `didRestore` after an undo or redo so the page reconciles its own state with the library (`LayoutEditorRules.reconciled`: shown version, active canvas, selection). It watches the library from `LayoutPageContent` (`.onChange(of: library)`), takes a before and after snapshot of each change and registers it on the Settings window's `@Environment(\.undoManager)` (so Cmd-Z, Shift-Cmd-Z and the Edit menu work); the names and folding are `LayoutEditHistory`'s. A canvas drag commits once on mouse-up, so it is one step. Right-click on a piece: `LayoutEditorRules.pieceMenu` / `title(for:isApp:)` (move to the other display, show/hide to everyone, show/hide on my screen, Remove; settled switches are not offered); on a card: Rename, Duplicate, Delete (Restore original stays hidden until P9). Keys are `LayoutKeyRules`: Esc cancels a drag in flight first (`cancelDrag`, `LayoutCanvas.dragCancelled`), then deselects; Tab walks `readingOrder` plus the camera (`cycleTarget`) and past the last piece lets go so the next canvas takes the keys; Delete on the camera says why (`removal`). Hover: a 1pt `Brand.green` outline on the tile under the pointer (not the selected one, not during a drag). VoiceOver (the camera's note is `cameraMoveNote`, from the camera state; the everyone / my screen actions are filtered by `offersEveryoneAction` / `offersMyScreenAction`): the canvas is a container named by `spokenCanvas`, each tile reads `spokenPiece` ("Chat, 3 of 12 columns, everyone sees it") with actions for move, resize, show/hide for everyone and on my screen, other display and Remove; the camera layer is a selectable button. Snapping guides, the dot grid and the live W x H readout were already built.

**Editor UI.** Layout editing lives in `App/UI` (`LayoutSettingsTab`, `LayoutCanvas`, `LayoutScreenPreview`, `LayoutAddPanel`) and is driven by `LayoutGeometry` (snap, overlap, minimums) and `LayoutTemplate`/`LayoutLibrary` mutators (`canAdd`, swap, duplicate). The camera overlay is selectable like a piece: its id is `LayoutCameraModel.selectionID` in the same `selection`, so picking one deselects the other; `PreviewCameraDragLayer(selected:onSelect:)` reports the click, and the inspector shows `cameraInspector` ("Who sees my camera" `GreenroomSegmented` of the four `CameraState`s = the saved default at each Start (`coordinator.setSavedCameraState`, writes `noCamera` and `cameraShownOnMyScreen` in step; global, every layout; the bar and Home change one meeting only, see codemap/stage.md)), a folded `CameraLookGroup` (App/UI/CameraLookControls.swift: Background Normal / Blur / Image with thumbnails and Choose..., Automatic / Green screen for Cutout and Presenter, Mirror; labelled "Same in every layout"; rows fold by `CameraLookRules`, bound through `LayoutCameraModel.look: CameraLookModel`). Delete on it does nothing. A deep link to the look (`SettingsTabs.destination(for:)`: the old "webcam" id and `SettingsTabs.cameraLookID`) sets `coordinator.layoutsCameraRequested`, and `LayoutPageContent.openCameraIfRequested` selects the camera and opens the group. `LayoutAppOrdering` (picker ordering, in UI) is pinned by `Tests/LayoutAppOrderingTests`. Starters are `LayoutLibrary.starters()`: `teach-browser`, `meeting-chat` and "Raj San Mode" (`rajMode` = "raj"; its `starter` tag only lets Reset to defaults restore it, it is edited like any layout).

**Threading.** `LayoutEngine`, `DisplayMonitor` and `withStartTimeout` operations are `@MainActor`; `MainPaneManager`/`AppWindowManager` are static enums with async waits (polling until an app has a window). `DisplayMonitor` registers a CoreGraphics reconfiguration callback and an NSApplication screen-change observer, both funnelled to main via `MainActor.assumeIsolated`.

## To change X, go to Y

- Change who sees a piece (badges, Preview: Everyone, capture) -> `Visibility` only; a new `LayoutPiece.Kind` or `ShareableWindow` will not compile until it has an answer. Canvas: `LayoutCanvas.badges` (eye = you, broadcast = everyone, amber when on; fixed answers are plain glyphs with the reason as help), the Preview: My screen / Everyone picker is `LayoutPageContent.previewPicker` (view state). DEBUG: Preview: Everyone calls `ShareVisibleWindows.crossCheck`.

- Add or change a piece kind (e.g. a new window type) -> `LayoutPiece.Kind` and its Codable in `LayoutTemplate.swift`; minimums/defaults in `LayoutGeometry.minimumPoints/defaultCells`; placement in `LayoutResolver.resolve.place` and `LayoutEngine.placeMeetingAndChat`.
- Add a new meeting view window -> `MeetingView` (case + `title`, append only; raw values are stored), `MeetingViewPieces.addEntries`, then the window side in `App/UI/MeetingVideo/` and `LayoutEngine.placeViews`.
- Change a built-in layout -> `LayoutLibrary.builtIns()` in `App/Layout/LayoutBuiltIns.swift` (`starters()` delegates; new starters need a `knownStarters` entry so `loadOrMigrate` appends them once; see `knownStartersKey`).
- One-time flip of old hidden pieces to shown -> `LayoutLibrary.showEverythingToEveryone()` (pure), run once by `loadOrMigrate` and recorded under `shownToEveryoneMigratedKey`; later hides survive.
- Change how a stored layout loads or migrates -> `LayoutLibrary.loadOrMigrate`, `firstRun(legacy:)`, `LegacyLayoutSettings.read/asTemplate`; fields decode optionally and via `Lossy<T>` so partial files load.
- Change snapping, grid or overlap rules in the editor -> `LayoutGeometry` (`stickyLines`, `snapMove`, `snapResize`, `limitResize`, `resolveDrop`).
- Change which display an arrangement goes on -> `LayoutResolver.resolve` (main always on main; second only when connected, `TwoDisplay.secondUUID`).
- Change the one-arrangement migration (ADR 0002, R27) -> `LayoutLibrary.migrateOneArrangement` (key `layoutLibrary.oneArrangementMigrated`, run first in `loadOrMigrate`; reads the old main through `TwoDisplay.legacyMain`; copy "<name> (old two-display)"; an untouched old Raj San Mode becomes the new one in place). Tests: `OneArrangementMigrationTests`, `OneArrangementResolverTests`, `OneArrangementModelTests`.
- Change what happens when the Meeting hides -> `LayoutResolver.absorbingNeighbour`, `frames(of:meetingHidden:)`, `LayoutEngine.moveNeighbour`.

- Change how another app's window is moved -> `AppWindowManager.setFrame/placeFrontWindow` (AX), `MainPaneManager.openWindow` (open path), `ChromeWindowManager` (AppleScript).
- Change which apps the picker offers -> `AppCatalog.installedAndRunning`, `isBrowser`; URL field handling -> `AppCatalog.normalizedWebURL/sanitizedURLText`.
- Change display-change settle time -> `DisplayMonitor.settleSeconds` (1.0) and `awaitQuiet`.
- Change what a display change does to the shared capture -> `DisplayPlan.decide`; where a stranded window goes -> `WindowRescue.rescuedFrame` and `DisplayMonitor.rescueStrandedWindows`.
- Look up a display by saved UUID -> `DisplayResolver.screen(forUUID:)`; list for pickers -> `connectedDisplays()`.
- Add a time limit to a Start step -> wrap it in `withStartTimeout(seconds, step:, advice:)` (see `hostAllInOne` for the pattern); the text IS the user message: say what did not happen and what to do.
- Change the Accessibility prompt/check -> `AppWindowManager.promptForAccessibilityPermission/hasAccessibilityPermission` (`ZoomWindowManager` just delegates).
- Change which app is focused after Start -> `LayoutEngine.activateLargestApp`, `LayoutResolver.largestAppOnMain`.

## Gotchas

- **Everyone sees (layouts with a second arrangement).** `TwoDisplay.sharedSlot` (key `sharedDisplay`, default main for old files) picks the display the meeting sees and recordings film. `CoordinatorController.effectiveCaptureDisplayUUID` feeds `StageConfiguration.displayUUID` (so the share and `SessionRecorder` follow): while the second arrangement is placed (`LayoutSharedDisplay.uuid`; no second display connected = nil = Screen choice stands) and the share is Whole screen, it overrides the global `screenCaptureDisplayUUID` (Settings -> Screen / Home) without changing it. `refreshCaptureDisplay()` re-pushes on library edit, Apply now and display change. A library edit mid-meeting never moves the shared display: `LayoutTemplate.adoptingEdit` keeps the running one until Apply now (R32.2). A Room screen forces main (`effectiveSharedSlot`; it can neither be added to a shared second nor can the second be shared with one), and the Room screen's own capture takes main. The camera overlay (editor canvas and Show on screen) sits on the shared canvas via `LayoutSharedDisplay.cameraSlot` (main when a shared second is not connected); the presence bubble follows the captured display; it is not a piece and never crosses displays by itself.
- **Dragging between displays.** `LayoutCanvas` reports the pointer in the pair's coordinate space (`LayoutCrossing`, frames via `LayoutCanvasFrames`); `LayoutSettingsTab.crossing(from:)` shows the landing box (`LayoutCrossPreview`) or the refusal and calls `movingPiece`. Option-left/right sends the selected piece across. Keys are `LayoutKeyRules`; a click calls `takeKeyboard()` (resigns the name field first).

- **Room screen.** `LayoutPiece.Kind.roomScreen` (coding `type` "roomScreen"; older builds drop it through `Lossy`) shows what the meeting sees on a big screen in the room, set as an EXTENDED display. A mirrored set is one NSScreen, so there is no `.second` slot: the resolver yields the one-display variant, `RoomScreenRules.placement` is nil and `LayoutEngine.placeRoomScreen` closes the window (a "switch to extended" prompt is a follow-up, not built). `canAdd` allows it only in `.second` (on the display it copies it would show itself). `LayoutEngine.placeMeetingAndChat` opens/places it; `CoordinatorController` calls `RoomScreen.setCompositor(stage)` after the scene's `stage.start` and `nil` in `stopStage`, `RoomScreen.close()` at Stop and quit; the layout's hide never reaches it (`RoomScreenRules.isHidden`): it stays up from Start to Stop. When the SDK reports a custom-UI state different from the saved setting, `LayoutEngine.customUIRuntime` is set in `presentMeetingSurfaces` and the layout is placed again (`LayoutResolver.viewsCanOpen`). Out of the share because `StageScreenSource(.display)` excludes the whole app, and out of other apps' recordings by `sharingType = .none`. Not verified without a real second display and a live meeting.

- **Two coordinate spaces.** `ns` is bottom-left (AppKit); `ax` is top-left of the PRIMARY display (AX and AppleScript). Always carry `LayoutFrames` rather than converting ad hoc (`LayoutGeometry.nsFrame/axFrame`, `primaryHeight`).
- **Stored as fractions, not pixels.** `UnitRect` is 0...1 of `visibleFrame` (excludes Dock and menu bar), origin top-left. Snapping only happens while editing, so a migrated off-grid layout is preserved exactly until touched.
- **Saved raw values are API.** `MeetingView` raw values, `LayoutPiece.Kind` coding keys (`type`, `fillsDisplay`, `startsHidden`, `app`, `view`) and `LayoutSlot` are persisted and exported; never rename. Decoding is lenient and drops bad pieces (`Lossy`).
- **Self view starts hidden on its own.** A Self view piece's "Starts hidden" does not join the all-together hide (`startsHidden` skips it via `SelfViewVisibility.joinsTogetherHide`); `placeViews` applies it.
- **Accessibility, not AppleScript, for most apps.** Without the grant every `AppWindowManager` setter silently does nothing; the grant is for Greenroom as a whole. Apps clamp below their minimum size: use the returned actual frame (`PlaceOutcome`, `fitNeighbour`).
- **Fullscreen windows ignore `setFrame`.** The meeting windows must be taken out of fullscreen before tiling (`ZoomMeetingSDKClient.exitFullScreen`, and the SDK is told not to auto-fullscreen at join).
- **Browsers get their own window.** Handing a URL to a running browser opens a tab in the existing window, and the session then tiles someone's tab pile; hence the scripted "make new window" route for every browser first (Ulaa uses Chrome's dictionary).
- **Never close what we did not open.** `closeApps` only touches the built-in browser and Chromium windows remembered by id.
- **Resolve every time.** Do not cache `Resolution` across display changes. Per-second loops must call `resolve` with `logNotes: false` or a fallback will be logged forever.
- **A display event is a burst.** Never act on a raw CG/NSScreen callback; use `DisplayMonitor.onChange` (settled) or `awaitQuiet`. A mirrored display set appears as ONE NSScreen (the mirror set's main), so a mirrored projector is never selectable on its own.
- **Xcode 27 SDK note:** `CGDisplayCreateUUIDFromDisplayID` moved to ColorSync; `DisplayResolver` gets it through AppKit, `LocalDeviceResolver` (Stage) imports it by name. Do not copy one file's imports into the other.
- **No layout is locked.** `starter` marks where a layout came from (Reset restores it, a duplicate drops it); it grants or removes no editing rights. `isRajAsShipped` (LayoutSettingsTab) is true only while Raj San Mode's pieces still match the shipped ones.
- **Starters use the Active speaker view** for their one-display speaker; Raj San Mode's second display keeps a full-display Meeting (the reference display). Where views cannot open (`meetingViews.enabled` off, meeting-window-only session) `LayoutResolver.substitutingMeetingForActiveSpeaker`, applied in `LayoutEngine.resolve`, swaps a lone Active speaker for the Meeting window in its rectangle. A layout with views and no Meeting piece never opens the Meeting window at Start (`meetingWindowWanted`); the control bar is the surface. Saved starters are not migrated (`addStarters` only adds new keys).
- **Meeting piece forms.** `.meeting(fillsDisplay: true)` is the Participants form: the whole display, opened by the participants window itself; `placeMeetingAndChat` returns early for it. It is editable: `LayoutEditorRules.adjusting` turns fill off on any hand edit (resize handles, drag), `settingFill` is the inspector's "Fill this display" switch.
- **Views need the Meeting window** (`MeetingViewPieces.addEntries(viewsEnabled:)`, default key `meetingViews.enabled`, tests set `MeetingViewPieces.override`).
- **Start timeouts own the failure text.** `StartTimeoutError`'s text (its `errorDescription`) is shown whole; it must name the step, the wait and the way out. `withStartTimeout` deliberately avoids a task group (it cannot return until every child ends).
- **Camera piece and What's shared are per layout (P3).** `LayoutTemplate.camera: LayoutCamera?` (spot, size, shape; App/Layout/LayoutCamera.swift) and `LayoutTemplate.share: ShareTarget?`; nil means the global settings stand (old files, no layout). The camera LOOK stays global (edited in the camera inspector). One-time migrations `layoutCameraMigrated` / `layoutShareMigrated` (`LayoutLibrary.migrateCameraAndShare`, run in `CoordinatorController.init`) copy today's globals into every layout; the old keys are kept. The coordinator's `webcamShape`, `bubble*`, `cutout*` and `shareTarget` are the LIVE working copy: `LayoutPieceAdoption` decides when a layout's pieces are put into it (Start, Stop, launch, a pick or an edit of the piece; `LayoutPieceAdoption.forLibraryEdit` is the one rule for a library change: with no meeting the active layout's changed camera or share flows into the working copy at once, and `adoptLayoutPieces` then asks the compositor to redraw (`Plan.refreshesPicture`, `requestShapeApply`) so Home's live preview and the bubble follow; it restores the global defaults after, so they stay the no-layout fallback). Only `LayoutEditSource.writesSavedLayout` callers write the layout: Settings -> Layouts (`commitPreviewPlacement(_:source: .settingsLayouts)`, the "Everyone sees this ▾" menu) (`saveCameraToActiveLayout`, via `LayoutLibrary.updateActive`; the shared-canvas pop-out writes the library directly); the Webcam tab is gone (P8), so `.settingsLayouts` is the only writer.
