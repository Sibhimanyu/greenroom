# App/Zoom

Greenroom's whole Zoom surface. Greenroom is the meeting client: it runs the native Zoom **Meeting SDK** in-process (`Vendor/ZoomSDK`, imported as `ZoomSDK`) in *custom UI* mode, signs in with an app JWT, starts the account's own meeting as host with a ZAK, sends Greenroom's composited stage picture as its camera through the SDK's external video source, and renders other people's video and shares into NSViews that the app's own windows host. Meetings are created, listed, edited and ended, and the ZAK fetched, over REST in one of two ways: as the person, after **Sign in with Zoom** (`ZoomUserAuth`, public PKCE client, no secret in the app), or with the pasted Server-to-Server app (`ZoomServerToServerClient`, "your own Zoom apps"). `ZoomRESTAccess` is the one switch; the coordinator picks with `ZoomRouteRules` (Settings' explicit choice). Everything that is not the SDK itself (budgets, ledgers, rules, parsers) is pure value code with no SDK import, so it can be unit-tested. The Zoom types are meant to stay behind this layer; outside callers get plain values (`RosterEntry`, `ShareRule`, `Bool` results).

Note: `startAsHost(... enableMedia: true)` is the real meeting client (camera and mic live, user's own name). `join(...)` still exists but the app never joins other people's meetings.

## How it fits

**Ownership.** `CoordinatorController` (App/CoordinatorController.swift) owns exactly one `let zoomChatClient = ZoomMeetingSDKClient()` (line ~497) and one `let zoomChatBridge = ZoomChatBridge()` (~498). The client owns three helper objects: `shareViewer` (`ShareViewer`), `viewVideo` (`ViewVideoStore`), `roomEvents` (`RoomEvents`). They are separate objects, not extensions, because they are SDK delegates. AppDelegate calls `zoomChatClient.shutdown()` on quit; `CoordinatorController` also calls `leave()` / `awaitMeetingClosed` on quit and `useStageVideo(nil)` when a session ends.

**SDK wrapper layering** (top = what the rest of the app sees):
1. `CoordinatorController` flows (`hostAllInOne`, `joinAllInOne`, `ensurePictureInstalled`, `runPipeline`) and UI (`MeetingControls`, `ParticipantGridWindow`, `MeetingViewWindow`, `PeoplePopOut`, `ChatWindow`) call `ZoomMeetingSDKClient` methods.
2. `ZoomMeetingSDKClient` (+ its extensions) is the only place that talks to `ZoomSDK.shared()` services (`getMeetingService`, `getSettingService`, `getAuthService`, `getRawDataController`).
3. Delegate objects feed events back: `ZoomSDKAuthDelegate`, `ZoomSDKMeetingServiceDelegate` (status), `ZoomSDKVideoContainerDelegate` (subscribe failures, data-type changes), `ZoomSDKMeetingActionControllerDelegate` (speaker, join/leave), `ShareViewer` (ASController + share container + share element), `RoomEvents` (waiting room + reactions), `ZoomChatBridge` (chat controller), `ZoomVideoSender` (virtual video source).
4. Pure value types (budget, ledgers, rules) sit beside and are called by the client, with no SDK import.
Callbacks to the UI are plain closures: `onVideoSubscribeFailure`, `onParticipantCountChanged`, `roomEvents.onChange/onWaitingJoin`, `shareViewer.onChange`. The UI polls once a second for roster/speaker state (`MeetingControls`, `ParticipantGridWindow`) and redraws at once on those closures.

**Auth, join, start flow** (host-only; no guest join):
1. Credentials load lazily via `SecretStore` (`zoomSDKClientSecret`, `zoomS2SClientSecret`; the Keychain item itself is read once at launch).
2. `ensureReady(clientID:clientSecret:)` (idempotent, de-duplicated through `authenticationTask`): `authenticate` runs `initSDK` once per process (`needCustomizedUI = true`; sets `didInit`), builds the JWT (`ZoomMeetingSDKJWT`), calls `sdkAuth`, and waits on `onZoomSDKAuthReturn` through `authCompletion` (watchdog `armAuthWatchdog`). After sign-in it logs the raw-data licence and calls `applyStageVideo()`.
3. Coordinator awaits `awaitMeetingIdle()` (only `Idle` is acceptable), `settleBeforeJoining()`, then `ensurePictureInstalled()` -> `awaitStageVideo()`; if it fails the start stops with `ZoomMeetingSDKError.videoInstallFailed`.
4. Host key: `ZoomServerToServerClient.startInstantMeeting` returns `CreatedMeeting.zak`; for scheduled meetings and the personal room `fetchZAK` (prefetched at pick time, valid < 600 s in the coordinator's `prefetchedZAK`). The personal room starts exactly like a scheduled meeting: its PMI as the meeting number with a fresh ZAK (the host needs no passcode and skips the waiting room); the log says "Starting your personal room as host…".
5. `startAsHost(meetingNumber:zak:displayName:enableMedia: true)`: sets `joinCompletion`, arms a 45 s join watchdog, sets `meetingService.delegate = self`, runs `suppressInteractiveJoinUI()` (no preview dialog, auto-join audio, hide-self-view pref, mirror off, spotlight-my-video off, no fullscreen at join, hide Zoom name labels in custom UI), then `startMeeting(withZAK:)`. The continuation resolves in `onMeetingStatusChange` (InMeeting = success; terminal states = `joinRejected(error,status)`).
6. In `onMeetingStatusChange` at Connecting/InMeeting, `adopt(container:)` claims the `ZoomSDKVideoContainer` (wires the container delegate), sets the action-controller delegate, installs `shareViewer` and `roomEvents` on the meeting service. Do this as early as Connecting so refusals are never unobserved.
7. Coordinator then `zoomChatBridge.attach(to: zoomChatClient.chatController())`.
8. `leave()` chooses `LeaveMeetingCmd_End` when `isHosting` or the live `getMyself().isHost()`; returns whether it asked Zoom to end. End: coordinator `endMeetingForEveryone(askedSDKToEnd:)` backs up with REST `endMeeting`. Quit: `shutdown()` -> `unInitSDK()`.

**Our camera (stage video).** `CoordinatorController.runPipeline` calls `useStageVideo(stage)` where `stage` is a `StageFrameSource` (see codemap/stage.md). `ZoomMeetingSDKClient` installs ONE `ZoomVideoSender` as the SDK's external video source after sign-in and keeps it for the SDK's life; sessions only `attach`/`detach` a picture. `ZoomVideoSender.stageDidRender` (called on the compositor's queue) stores the newest `CVPixelBuffer` under `frameLock`; a `DispatchSourceTimer` on queue `greenroom.zoomvideosender` sends the latest frame converted by `I420Converter` at the rate the SDK suggested in `onInitialize/onPropertyChange`. `onReleased` (main queue) marks it uninstalled so the next start reinstalls.

**Video and share subscription.** Custom UI means Zoom draws nothing; every view comes from an element:
- Elements are `ZoomSDKNormalVideoElement`s made by `videoContainer.createNormalVideoElement`, owned by one NSView host. Three families: tiles (`participantElements[userID]`, `participantView`), the Meeting window's stage (`stageElement`, `stageView`), and View-window elements (`ViewVideoStore.entries[ViewVideoKey(view, slot)]`, `viewVideoView`). Plus `railSelfElement` (own picture, `makeRailSelfView`).
- Order: make element (setting `userid` already subscribes it on macOS) -> caller puts its view in a VISIBLE window -> a later layout pass sets `setResolution`, shows the view, and calls `subscribeVideo(true)` ONLY if `getDataType()` is still None (`paceSubscribe` returns `implicit: true` when it skipped the call). Subscribing before the view is visible never draws.
- Resolution tier comes from `VideoBudget.allocate` (View windows) or `ZoomMeetingSDKClient.resolution(for:openStreams:hero:)` (Meeting window tiles); `meetingWindowVideoUsage()` reports what the Meeting window holds so the budget sees it as external usage.
- A refusal arrives in `onSubscribeUserFail` AFTER `subscribeVideo` returned success. Routing: view-window element -> `noteViewVideoFailure`; stage -> `stageBackoff`/`stageWatch`; tile -> `tileBackoff[userID]`/`tileWatch`. Code 7 means slow down: the refusal is waited out at least `ElementRecovery.refusalGrace` (8 s, else the `SubscribeBackoff` 2..32 s). Then: avatar (camera off) -> `.recovered`, never retired; video or None -> one retry on the SAME element (`.retry`, `readyToRetry` repeats the refused request: setResolution again on an element subscribed by `userid`, the subscribe after an explicit ask); still refused -> fresh element (`.rebuild`, max 3, 1.5 s fresh delay), then give up until the camera comes back on. Data type Video is NOT proof of frames: on 2026-11-26 02:14Z four refused Active speaker elements reported Video, were kept, and stayed dark. The refusal lines and the retry carry `layerProbe` (layers with contents and a contents signature) to show whether frames moved. Every setResolution and subscribe call goes through `paceSubscribe` and the one app-wide `subscribeThrottle` (0.5 s apart; setResolution and its retry and an explicit subscribe are separate slots, but when the data type is already not None, setResolution and the show/subscribed bookkeeping share ONE slot, since neither is a subscribe call).
- Shares: `ShareViewer` tracks `onSharingStatusChanged` (OtherBegin/End, SelfBegin/End), keeps `selection: ShareStageSelection`, makes a `ZoomSDKShareElement` for one source, hands out its view via `stageView(frame:)`, and calls `ShowShareRender` only once the view is in a visible window (`renderIfReady`). One window can draw a source at a time (`setWindowOwnsShare`).
- Active speaker: `noteActiveAudio` (audio event) and `noteActiveSpeaker` (Zoom's pick) feed `speakerToShow()`; silence keeps the last speaker. `RecentSpeakers` feeds Multi-speaker places via `multiSpeakerPlaces(roster:)`. `stagePerson()` = spotlighted, else pinned, else `speakerToShow()`.

**Threading.** `ZoomMeetingSDKClient` is `@MainActor`; SDK delegate callbacks are delivered on the main thread and used directly. Exceptions: `nonisolated static` helpers (`statusName`, `errorName`, `logLicenceLine`, which hops to main for `CoordinatorController.sessionLog`); `ZoomVideoSender` is NOT main-actor: `frameLock` guards the shared frame, everything else is touched only on its serial `queue` (`isSending` uses `queue.sync`), and it hops to main for `onReleased`. `ZoomServerToServerClient` is static async, with `tokenLock` (NSLock) around the token cache. `ZoomChatBridge` is a plain (non-actor) NSObject published to SwiftUI and assumes SDK delegate callbacks arrive on the main thread. `ParticipantAvatarStore` is an `ObservableObject` singleton updated from `avatarPathUpdated`.

**Logging.** `ZoomMeetingSDKClient.videoLog` appends to `~/Library/Logs/Greenroom-video.log` (prefixes "View window:", "Share view:", "Room:"); `logLicenceLine` goes to the in-app session log and os_log (subsystem `com.sibhimanyu.greenroom`, category `zoom`), prefix "Meeting video:" for the sender.

Ending a meeting over REST and reading meeting details need scopes the user token does not have yet; the in-meeting SDK end is the main path.

## Gotchas

- **Custom UI is the only mode.** Zoom's own meeting window mode was removed 2026-11-25 (`docs/specs/remove-zoom-window-mode.md`; restore from git tag `zoom-own-window-mode-last`). `customUIMode` survives only as a retired field in the settings file (decoded, ignored).
- **Custom UI is an init parameter.** `needCustomizedUI` is read once at `initSDK`; it is always true. Check `didInit` before returning views (`participantView`, `stageView`, `viewVideoView` return nil otherwise).
- **Setting `userid` subscribes; do not ask again.** On macOS an explicit `subscribeVideo(true)` on an element whose `getDataType()` is Video or Avatar is refused with code 7 (2026-11-23: 88 of 88, dataType already 1 or 2). Call it only at data type None. On a `userid`-subscribed element the setResolution is the second request, and it is what Zoom refuses with code 7 (every refusal in the log follows a setResolution that returned 0). An avatar (camera off) forgets a refusal; Video does not (see the refusal routing above). A new speaker is the SAME element with a new `userid` (stage and View slots; log "switched user A -> B on same element", 2 s guard kept, watch reset with resolution kept); a fresh element is only the recovery fallback. Every path that cleans an element also calls `getVideoView().removeFromSuperview()`, or the last frame stays frozen on screen. A second element asking for a remote user another element holds is also refused (`otherHolders` names them in the log).
- **Do not subscribe in bursts.** All SDK subscribe/setResolution calls share one 0.5 s `subscribeThrottle` (stage, tiles, view windows), stage switches rate-limited (`nextStageSwitchAt`), View slots 2 s apart per slot.
- **View height can silently become a 1080p request** when `setResolution` is not in effect (>= 850 pt tall). Set resolution before subscribing; the quota is spent at subscribe time. We never ask for 1080p (`VideoTier.p720.quota` counts the shared 1080p/720p slots).
- **Refusals arrive after success** and come in clusters of 2-3 at the same instant; `ElementWatch.isRepeatRefusal` (< 1 s) treats them as one.
- **Layer count is not a drawing signal** (four sublayers appear before any subscribe); it is logged only.
- **Start only from Idle.** `awaitMeetingIdle()` waits for `Idle` (not `Ended`): a late terminal status from the previous meeting otherwise fails the new join ("meeting ended before Greenroom finished joining"). `awaitMeetingClosed` (accepts Ended/Failed) is for quit only.
- **Install the video source once.** `setExternalVideoSource` can fail with `Malloc_Failed (22)` if called around display changes; it waits on `DisplayMonitor.shared.awaitQuiet` and only clear-and-reinstalls on retry. Never swap/clear the source between meetings; `shutdown()` is the only normal reset (it nils the sender so the next sign-in reinstalls). The SDK holds the source delegate weakly, so `stageVideoSender` must stay referenced.
- **Container and event delegates must be claimed at Connecting**, not on first tile, or early refusals go unreported.
- **Shutdown order matters.** Quit must `leave()` + `awaitMeetingClosed` + `shutdown()` (`unInitSDK`); exiting around the SDK's video/audio engines SEGVs in their destructors.
- **ZoomSDKError etc. are C `typedef enum`s**, so cases are top-level constants (`ZoomSDKError_Success`), not dot-syntax. `errorName` must be extended when new codes matter.
- **`ZoomSDKMeetingError_None` (101) means "no reason given"**, not a rejection; `joinFailureText` handles it.
- **Cross-account joins** hit `ZoomSDKMeetingError_UnableToJoinExternalMeeting` (63); `ZoomMeetingSDKError.isCrossAccountRejection` exposes this without importing ZoomSDK elsewhere. Proven 2026-11-26: signed in with an account other than the one owning Greenroom's Zoom app, a meeting created on that account and started with its own ZAK is refused at Connecting with 63. Zoom staff (devforum 145559, 146160, Aug-Sep 2026): a Meeting SDK app cannot start meetings for external users, published or not. `ZoomRefusalRules` (in `ZoomRouteRules.swift`) words it (`startFailure`: why, what to do, the route line, `StartFailureFix.openOwnZoomApps` so the island's button reads Open Settings and unfolds "Use your own Zoom apps" via `CoordinatorController.openZoomOwnApps`/`zoomOwnAppsRequested`), and remembers the refused account ID (`zoomRefusedAccounts`, key `zoomRefusedAccountIDs`) so Home's pill and Settings warn before the next Start; a Start that goes live clears it. There is no reliable pre-check before the first refusal: the app owner's account ID is not known to the client (the JWT carries only the client ID, and the signing function must not change). `joinAllInOne` rethrows this error unwrapped so the type survives.
- **The client secret never ships.** Only the public client ID is in the app; the confidential secret lives in the Catalyst function's environment.
- **Secrets are in the Keychain, one item, no prompts (owner, 2026-11-26).** `SecretStore` keeps every secret in one generic-password item in the login keychain (after first unlock, this device only, not synchronizable), read once per launch into memory. Never call SecItem per read or per redraw, and never write the item after a failed read (it would wipe what it holds). Not the data-protection keychain: it needs `keychain-access-groups`, which macOS kills the app for without a provisioning profile (checked 2026-11-26), and Greenroom ships signed with the Apple Development certificate and no profile. The login keychain reads silently for any build carrying that same certificate (Debug, Release, Sparkle updates); a build signed by anything else (ad hoc, another certificate, a future Developer ID) gets one "Greenroom wants to use your confidential information" dialog for the item. Migration (`SecretVault.migrateIfNeeded`, flag `secretsInKeychainMigrated`): UserDefaults `secret_*` and the old Zoom item (service `com.sibhimanyu.greenroom.zoom`) are copied in, read back, and only then deleted; on failure nothing is deleted, `get` falls back to the old copy, and the next launch tries again. The three client secrets still travel in the settings file (plain text, after the warning); the refresh tokens do not.
- **Debug-only:** `startDebugTestPatternIfEnabled` (`GreenroomRawVideoSpike`) feeds a test pattern through the real sender; must stay behind `#if DEBUG`.
- **Pure files must stay SDK-free** (`VideoBudget`, `SubscribeBackoff`, `RecentSpeakers`, `HandsUpOrdering`, `MeetingRoomLedgers`, `MeetingShareRules`, `NewMeetingRequest`, `I420Converter`, `ZoomScopes`, `ZoomMeetingLinkParser`, `ZoomUserAuthRules`, `ZoomRouteRules`, `ZoomSetupCheckRules`, `ZoomCheckActionRules`, `ZoomMarketplacePages`, `ZoomGuideFollowRules`, `ZoomCoachRules`, `ZoomPersonalRoom`): the tests and offline tools compile them without `ZoomSDK`.
- **Tests that pin this area** (Tests/): `VideoBudgetTests`, `SubscribeBackoffTests`, `RecentSpeakersTests`, `HandsUpOrderingTests`, `NewMeetingRequestTests` (also `ZoomScopes`), `MeetingToolbarTests` (`WaitingRoomLedger`, `ReactionLedger`, `ShareRule`, `ShareStageSelection`, `ChatWho`, `ZoomAppLink`), `MeetingViewRulesTests` (`RecentSpeakers`), `ZoomUserAuthRulesTests`, `ZoomRouteRulesTests`, `ZoomSignInComingSoonTests`, `ZoomGuideFlowRulesTests` (route precedence and words), `ZoomRefusalRulesTests` (error 63 words, fix button, remembered refusals), `NotchStatusRulesTests` (the failure's button title), `ZoomSetupCheckRulesTests` (sign-in check table, shared summary, JWT appKey), `ZoomCheckActionRulesTests` (check line buttons, fix bar, error sorting), `PersonalRoomTests` (PMI parse, list order, missing scope, scope line, number format, words); the function has `node --test` tests in `server/sdk-signature/test`. Not covered: `StageVideoSizing`, `I420Converter`, `ZoomMeetingLinkParser`, the SDK client itself.
- **Reaction clean-up** uses `DispatchQueue.main.asyncAfter(ReactionLedger.lifetime + 0.1)` in `RoomEvents`; keep `reactions.prune` in step with `pruneReactions(present:)` (called from the toolbar poll).
- **Stale `callbackGeneration`**: watchdogs compare it; `abandonPendingCallbacks()` bumps it and cancels pending auth/join continuations with `CancellationError`. Any new awaited-callback must follow the same continuation + generation pattern or it will hang the Start flow.
